# Modal: приватный сервис и диагностика

В проекте два отдельных режима. `modal_inference.py` развёртывает действующий приватный сервис для модельных запросов сайта. `modal_evaluation.py` запускает одноразовую синтетическую диагностику во временном App. Их списки отправки, время жизни контейнера и результаты различаются. Все команды ниже выполняются из корня проекта.

## SDK и авторизация

Лексическая часть сайта использует стандартную библиотеку Python. Для приватного сервиса и диагностических запусков нужен Modal SDK. SDK 1.6.3 уже установлен в отдельное исключённое из Git окружение `.runtime/modal-venv`. Для нового рабочего экземпляра:

```sh
python3 -m venv .runtime/modal-venv
.runtime/modal-venv/bin/python -m pip install modal==1.6.3
```

Владелец подтверждает авторизацию SDK в браузере. В текущем экземпляре доступ предоставлен на 12 часов. При подготовке новой авторизации команда задаёт срок и отдельный путь конфигурации:

```sh
MODAL_CONFIG_PATH=.runtime/modal-config.toml .runtime/modal-venv/bin/python -m modal token new --expires-in 12h
chmod 600 .runtime/modal-config.toml
```

Содержимое `.runtime/modal-config.toml` не выводится, не отправляется в контейнер и не публикуется. Весь `.runtime/`, включая SDK-окружение, токен, manifest и журналы вызовов, исключён из Git. Истечение или отзыв авторизации может обнаружиться только при явном облачном запросе; локальный статус не проверяет токен через сеть. [Установка и настройка Modal](https://modal.com/docs/guide).

В аккаунте перед запусками проверены Starter, предоставленные $30, custom Spend limit $0 и Usage limit $30. Эти настройки относятся к аккаунту. Ограничение числа контейнеров само по себе не является денежным лимитом. Фактический текущий расход проверяется отдельно в Modal.

## Действующий приватный сервис сайта

[App `istok-inference`](https://modal.com/apps/zhanlaiman/main/deployed/istok-inference) содержит приватную Class `OllamaService`. Сейчас выбраны `qwen3.5:9b` и `bge-m3:latest`; выбранная версия Qwen описана в [результатах испытаний](../docs/MODEL_RESULTS.md). И Qwen, и BGE вычисляются удалённо. Сайт, библиотека, SQLite и кеш представлений остаются на Mac.

У Class одна L40S, четыре CPU, 32 GiB запрошенной системной памяти, `min_containers=0`, `max_containers=1`, `buffer_containers=0`, `scaledown_window=60` и `retries=0`. Подготовка ограничена 600 секундами, один метод — 180 секундами; внутренний HTTP-запрос к Ollama — 170 секундами. Клиент ждёт подготовку отдельно от времени ответа: по умолчанию `600 + 180` секунд. Генерации и embeddings сериализованы.

Постоянные Volumes, расписания и публичные модельные HTTP endpoints не создаются. При первом явном compute-запросе контейнер запускает Ollama на loopback и получает две модели во временный `/tmp/istok-models`. Холодная загрузка весов занимает оплачиваемое GPU-время. После простоя сервис масштабируется к нулю; выходной обработчик завершает Ollama. Развёрнутый App может оставаться доступным без активной GPU. После живой проверки число активных контейнеров и расходы подтверждаются отдельно в интерфейсе Modal. [Параметры простоя и холодного запуска](https://modal.com/docs/guide/cold-start).

### Локальный план без SDK-вызова

Команда читает уже сохранённый файл инструментирования, собирает SHA256 исходников и выводит план. Она не импортирует Modal SDK, не развёртывает App, не скачивает веса, не вызывает модель и не записывает runtime manifest:

```sh
python3 -m cloud.modal_inference \
  --benchmark-resources data/runs/modal-qwen9b-v5-cloud-20261111-resources.json \
  --model qwen3.5:9b
```

`--benchmark-resources` принимает именно `-resources.json` с `runtime.installed_models.models` и реальными digest, а не основной JSON с метриками. Файл должен содержать выбранную Qwen и `bge-m3:latest`. Артефакты `data/runs/` исключены из Git; на новой машине нужно отдельно получить проверенный файл. Скрипт не придумывает контрольные суммы по имени модели.

### Явное развёртывание

Следующая команда действительно размещает приватный App в окружении `main` и после успешного размещения атомарно записывает локальный manifest:

```sh
MODAL_CONFIG_PATH=.runtime/modal-config.toml .runtime/modal-venv/bin/python -m cloud.modal_inference \
  --benchmark-resources data/runs/modal-qwen9b-v5-cloud-20261111-resources.json \
  --model qwen3.5:9b \
  --output .runtime/cloud-models.json \
  --deploy
```

Развёртывание не выполняет тестовый запрос к модели; при `min_containers=0` ему не требуется прогрев GPU. Первый вызов `/api/chat` или `/api/embed` запускает модельную работу.

В образ включаются ровно два файла из `FILES`: `cloud/modal_inference.py` и `plagiarism/cloud_contract.py`. Проверяются пути, отсутствие символических ссылок и SHA256. Автоматическая отправка исходной папки отключена через `include_source=False`. Рабочая SQLite, `.runtime/`, авторизация и документы в образ не входят. Образ Ollama 0.34.2 закреплён по amd64 digest.

### Runtime manifest и проверка версии

`.runtime/cloud-models.json` содержит `provider=modal`, app/class/environment, `deployment_id`, полученный при deploy `class_id`, `default_model`, `embedding_model`, список моделей с настоящими digest и capabilities, `verified_at`, `synthetic_only=true`, настройки подготовки и закреплённый образ. Секретов в manifest нет.

`deployment_id` вычисляется из двух исходных файлов, выбранных моделей и образа. При входе в контейнер повторно сверяются SHA256 файлов и фактические digest обеих загруженных моделей. Клиент при compute сверяет Class ID и версию deployment, затем проверяет digest из ответа. Несовпадение останавливает запрос. Изменение gateway/contract или выбранных весов требует согласованного развёртывания и manifest; вручную заменять digest для обхода проверки нельзя.

По умолчанию транспорт читает `.runtime/cloud-models.json`; альтернативный путь задаёт `ISTOK_CLOUD_MANIFEST`, runtime-каталог — `ISTOK_RUNTIME_DIR`. Произвольные модели и операции pull/delete/generate через transport запрещены. Из клиентских RPC доступны только проверенные `/api/chat` и `/api/embed`.

### Запуск сайта с облачным транспортом

При наличии manifest обычный launcher автоматически выбирает Modal и интерпретатор `.runtime/modal-venv/bin/python`:

```sh
python3 scripts/start.py
```

Явный выбор того же провайдера:

```sh
ISTOK_MODEL_PROVIDER=modal python3 scripts/start.py
```

Вместо launcher сервер можно запустить напрямую:

```sh
ISTOK_MODEL_PROVIDER=modal MODAL_CONFIG_PATH=.runtime/modal-config.toml \
  .runtime/modal-venv/bin/python server.py --port 8766
```

Используется один из этих вариантов запуска. Сайт остаётся на `http://127.0.0.1:8766`; публичный веб-хостинг не создаётся. Маркер `.runtime/local-inference-disabled` сохраняется. По требованию пользователя локальные Qwen удалены, локальная BGE остановлена: повторно скачивать/запускать их или снимать маркер без нового явного разрешения нельзя. При недоступном облаке сайт сообщает об ошибке и не переключается на локальную Ollama.

### Статус, задания и данные

`/api/status`, главная страница и `/api/tags` не вызывают GPU Class. Статус каждые 15 секунд читает только локальные manifest и `.runtime/cloud-health.json`; SDK импортируется лениво при явном compute. Поля `configured/can_submit` означают готовность конфигурации принять запрос, а не подтверждённую текущую авторизацию или прогретую GPU. Digest из локального `/api/tags` используется существующим EmbeddingCache. Реальная проверка 100 HTTP-опросов статуса добавила ноль облачных вызовов; локальный артефакт — `data/runs/site-cloud-status-check.json`.

Одиночные сравнения, правки и учебная оценка сайта выполняются через `/api/model-jobs`. Постоянный `request_id` защищает от повторного compute, результат или ошибка сохраняются в SQLite. После обновления страницы наблюдение восстанавливается через GET. Незавершённый при перезапуске запрос становится `job_interrupted` без автоматической повторной генерации. При таймауте транспорт отменяет именно свой SDK call; идентификатор и результат отмены сохраняются в `.runtime/cloud-calls/` без текстов и секретов. Остановка после сбоя отмены не объявляется подтверждённой.

Приватный SDK не передаёт браузеру токен или прямой публичный адрес модели. При явной модельной проверке выбранные текстовые фрагменты передаются Modal как аргументы RPC. Отсутствие Volumes не означает обещания нулевого временного хранения данных провайдером. В текущем QA разрешены только авторские синтетические данные, демо и открытые фрагменты; личный черновик и документы не отправляются. `synthetic_only=true` обозначает этот тестовый этап и сам по себе не классифицирует введённый текст.

Сервис сохраняет прежние границы доказательств: выбор исходных предложений, точные позиции и проверка буквальной метки остаются в адаптере; актуальность положительной оценки и границы правки проверяются на сайте. Direct embed/judge и учебная оценка через UI проверены; общие результаты описаны в [README проекта](../README.md) и [HANDOFF](../HANDOFF.md).

## Одноразовая синтетическая диагностика

Подготовлен отдельный запуск Qwen на одной L40S 48 GB. По умолчанию используется Qwen3-32B Q4_K_M. Параметр `--model` принимает `qwen3:4b`, `qwen3.5:9b` и `qwen3:32b-q4_K_M`. Функция вызывается через приватный Python SDK внутри временного App. Максимум один контейнер, четыре CPU, 32 GiB запрошенной системной памяти и час выполнения. После одного задания контейнер завершается. Эти параметры ограничивают вычисления одного App. Денежный лимит задаётся в аккаунте Modal.

Для первого прогона в интерфейсе Modal проверены тариф Starter, предоставленные $30, custom Spend limit $0 и Usage limit $30. Эти настройки относятся к аккаунту. Авторизация SDK выполняется владельцем отдельно.

### Что отправляется

Пофайловый список `UPLOAD_FILES` в `modal_evaluation.py` содержит 18 файлов: исходные Python-модули `plagiarism`, два необходимых скрипта, сам управляющий скрипт и два авторских синтетических JSON-набора. В список входят `cloud_transport.py` и `cloud_contract.py`, необходимые для импорта адаптера. Перед отправкой вычисляются SHA256. Символические ссылки отклоняются, автоматическое включение исходной папки Modal отключено.

Проверить конкретный список локально можно без Modal SDK и без аккаунта

```sh
python3 -m cloud.modal_evaluation
```

Веса, SQLite и контрольные ответы хранятся только на временном диске контейнера. Постоянные Modal Volumes не создаются. Локальные `.runtime`, SQLite, документы и пользовательская библиотека в список отправки не входят.

### Явный запуск

```sh
MODAL_CONFIG_PATH=.runtime/modal-config.toml .runtime/modal-venv/bin/python -m cloud.modal_evaluation --run
```

Для полного прогона 9B на том же типе GPU

```sh
MODAL_CONFIG_PATH=.runtime/modal-config.toml .runtime/modal-venv/bin/python -m cloud.modal_evaluation --run --model qwen3.5:9b
```

В контейнере стартует Ollama на loopback-адресе. Провайдер внутри контейнера явно установлен в `ISTOK_MODEL_PROVIDER=local`: запросы идут в эту Ollama и не перенаправляются в отдельный облачный шлюз проекта. Это настройка удалённого контейнера; локальные модели на Mac она не включает. Загружаются только `bge-m3` и выбранная Qwen. Контроллер исполняет существующий `scripts/evaluate_pipeline.py` с неизменёнными инструкциями модели и полным разделом `test`, по пять кандидатов на статью. Поиск может держать обе модели в памяти. Параллельная генерация отключена.

Файлы вернутся в локальный `data/runs` с идентификатором прогона. Основной JSON совместим со скриптом сравнения. Отдельный файл `-resources.json` содержит версию Ollama, закреплённый образ и его digest, Modal Image ID, модельные метаданные, измерения ресурсов и время запросов. В нём раздельно указаны время подготовки с загрузкой весов и полное время работы контейнера. Содержимое внутреннего рассуждения модели не сохраняется.

Код выхода 1 может сопровождать полноценный отчёт с неопределёнными ответами. Он сохраняется вместе с ошибками и метриками. Техническая ошибка запуска отмечается отдельно в `execution_error`.

Каждый вызов выполняет свежий прогон в новом контейнере. Кеш представлений переиспользуется только внутри этого вызова. Отчёт сохраняет фактические `model_calls` и `cache_hits`. Веса загружаются заново при следующем вызове.

### Хранение и границы проверки

SQLite и JSON-кеши работают на временном локальном диске контейнера. После возврата результата контейнер завершается и его временные данные удаляются. Принудительное уничтожение контейнера до возврата результата может потерять текущий прогон. Постоянное хранение весов и восстановление прерванного облачного прогона в этом варианте отсутствуют. Длительность загрузки весов входит во время работающего GPU-контейнера и учитывается отдельно от собственно проверки.

Подготовка проверена локальными тестами списка файлов, синтетических данных, безопасных идентификаторов, выбора модели и сохранения JSON при диагностическом коде выхода 1. Полные серверные прогоны 4B, 9B и 32B завершены; результаты и отдельный прогон 9B с адаптером v5 описаны в [сравнении моделей](../docs/MODEL_RESULTS.md). Синтетические примеры используются для отладки и не оценивают точность на новых реальных работах.

Официальные источники подтверждают временный SDK-вызов, настройки контейнеров, L40S и явное включение файлов. Образ Ollama 0.34.2 закреплён по amd64 digest из публичного Docker Hub.

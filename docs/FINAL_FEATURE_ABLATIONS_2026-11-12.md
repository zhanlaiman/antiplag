# Раздельная проверка URL, PDF и явно названной статьи

Фактический итог последующего свежего прогона всех 30 — **231/283**, описан отдельно в [FINAL_FRESH30_2026-11-12.md](FINAL_FRESH30_2026-11-12.md). Приведённые ниже 264/283 — условный повтор прежних сохранённых ответов и страниц.

Три последовательных запуска обычного production `web_search.run` на одинаковых сохранённых DEV30-ответах показывают отдельный вклад изменений: **248 → 249 → 264** покрытых заимствованных слова из 283. Дополнительное PDF-представление восстанавливает одно слово D06; чтение явно названной в самом тексте статьи восстанавливает цитату D14 из 15 слов. D01 и D02 остаются пропусками поиска нужной ссылки.

Все результаты ниже — **локальные повторы сохранённой выдачи и страниц**. В этом сравнении новых поисковых запросов и загрузок страниц нет. Скрипт не создаёт поисковый API-клиент или обычный сетевой Fetcher, а socket audit hook запрещает сеть. Финальные 70 и незнакомые отложенные примеры не используются.

## Три варианта, один порядок сравнения

1. Слова пути URL + бюджет полезных переходов, только основное извлечение текста.
2. Тот же вариант с сохранённым PDFium-представлением того же PDF. Основной текст остаётся тем же, представление передаётся отдельно и проходит production-проверку порядка исходных символов.
3. Тот же вариант с `use_named_references=True`: название статьи извлекается production-парсером только из явной ссылки в самом документе. Название остаётся непроверенным указанием источника до сопоставления текста.

|---|---:|---:|---:|
| Проверено документов | 30 | 30 | 30 |
| Ожидаемые пары документ–источник обнаружены | 11/28 | 11/28 | 12/28 |

«Любой подтверждённый источник» включает проверенные буквальные перепечатки и зеркала. Это не означает, что найден именно исходный URL. Смысловые фрагменты (11) исключены из знаменателя буквальной подсветки. Добавленное автором слово D10 не входит в заимствованные 283 слова: используется общий `copied_target_tokens` и проверка привязки обеих выдержек через анализатор DEV-отчётов.

Подтверждённый ложный результат в таблице — ранее рассмотренное необоснованное расширение `similar`. Он не охватывает все теоретические ошибки атрибуции. Неожиданные буквальные совпадения сверяются отдельно; совпадение общепринятой юридической формулировки D19 не доказывает её происхождение.

## Что именно изменилось

- D06: **7 → 8 → 8** заимствованных слов. Дополнительное представление восстановило целое слово из PDF. В очередь не добавился новый физический источник или запрос.
- D14: **0 → 0 → 15**. Ссылка построена из явного названия статьи в тексте, а выдержка подтверждена реальным ранее сохранённым ответом обычного Fetcher. Поисковые фразы и выдача не менялись. Источник показан с цитатой; неподтверждённое название само по себе не создаёт подсветку.
- D04: ранее восстановленные **7** слов сохранены во всех вариантах.
- D09: восстановленные **29** слов сохранены; D12 — **55**, D20 — **25**.
- Инкрементальные изменения PDF и явной статьи не потеряли ни одного прочитанного физического источника. Это не отменяет ранее записанную потерю дополнительного dslov-источника D12 при введении приоритета пути URL: полное покрытие D12 сохранялось из FEB.

В кэше доступны три сохранённых PDFium payload (D06/D16/D20), но из выбранных страниц именно этого сравнения дополнительное представление использовано только в D06. Нельзя выдавать доступность трёх payload за три успешно проверенных PDF-источника в новой очереди.

## Почему это ещё неполная проверка интернета

В каждом варианте воспроизведено **167 сохранённых вызовов** планировщика поиска; новых API-вызовов — **0**. Варианты делают по **358** попыток чтения из кэша в сумме, не более двенадцати на документ. Прочитано физических источников **178 → 178 → 179**. Дополнительный PDF view физическим источником не считается.

Исторические прогоны не сохранили содержимое каждой потенциально выбранной страницы. Неизвестных загрузок кэша: **176 → 176 → 175**. У **14/30** документов хотя бы одна сохранённая страница не содержит исходных подписей ссылок. Поэтому **все 30 повторов помечены partial**, а итоговая уникальность не устанавливается. Содержимое отсутствующих страниц не выдумывается и не загружается для заполнения сравнения. Частичная проверка в интерфейсе должна оставаться частичной.

Первый вариант при этом воспроизводит число найденных слов предыдущего проверенного `path+productive` повтора **30/30**. Это контроль сопоставимости имеющихся данных, а не заявление о полноте загрузок.

## Проверка происхождения сохранённых данных

PDF payload берутся только из `pdf-production-validation-v1/D06-fetched.json`, `D16-fetched.json`, `D20-fetched.json`. Проверяются SHA основного текста и view, общий raw-PDF SHA, число страниц, extraction/parser identity. View прикрепляется только после совпадения SHA основного текста с фактически выбранной страницей. Основной текст и подписи ссылок не заменяются свежим PDF payload.

Единственная дополнительная страница для явного указания источника берётся из `dev-named-reference-v1/D14-fetch-response.json`: один ранее разрешённый обычный Fetcher GET от `2026-11-11T20:01:44.610535+00:00`. Input SHA, полученный из самого ввода URL и SHA текста страницы проверяются до использования. Страница доступна в одинаковом кэше для всех вариантов; право добавить её в очередь меняет только production input parser и флаг. В ходе этого сравнения запрос не повторяется.

Скрипт сохраняет SHA исходного кода, файлов с ответами, primary/view текстов, исходный run каждого случая и все добавленные/удалённые пары выдержек. Изменение production-кода во время расчёта останавливает выпуск сводки.

## Воспроизведение

```sh
python3 scripts/replay_final_feature_ablations.py
```

Результат: `data/private/web-evaluation/dev-final-feature-ablations-v1/comparison.json`; три подкаталога содержат по 30 обычных production-отчётов и `analysis.json`. В `incremental_match_and_source_deltas` записаны обе стороны каждого добавленного или снятого совпадения и потери физических источников. Главный источник метрик — общий `scripts/analyze_web_dev_checks.py`, а не отдельный подогнанный счётчик.

Проверки чистоты данных находятся в `tests/test_final_feature_ablations.py`. Применение новых флагов по умолчанию, свежий HTTP-прогон, UI-проверка и полный набор серверных/интерфейсных тестов отражаются отдельно в утреннем отчёте.

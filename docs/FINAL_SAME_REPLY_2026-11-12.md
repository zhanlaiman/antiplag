# BALANCED и PATH на одной финальной выдаче

Обычный production `run` получил одни и те же сохранённые ответы всех 30 финальных DEV-проверок. Остальные признаки зафиксированы: DENSE, полезные переходы, named references, доступные сохранённые PDF-представления. PATH воспроизвёл все 30 фактических отчётов по совпадениям, полным SHA источников, числу прочитанных страниц и порядку физических попыток.

Сначала у BALANCED не хватало 26 снимков страниц. По отдельному разрешению выполнены **26 обычных Fetcher GET**: 19 успешных, семь с сохранённой причиной отказа. Никакие исходные финальные страницы, ошибки и ответы поисковика не менялись. Затем оба порядка повторены **без сети** на дополненном одинаковом кэше. Дополнительных поисковых API-вызовов: **0**. Из разрешённого предела 48 использовано 26; повторов тех же неудачных/неизвестных попыток не было.

Единственная разница в покрытии ожидаемых слов — D09, **24 → 29**. Прежние три неизвестные страницы BALANCED теперь имеют снимки; пяти недостающих слов они не добавили. Контроль D04 остаётся 7/7, D06 — 8/8. Потерь ранее найденных скопированных слов в этих сохранённых данных нет.

Есть потеря дополнительного подтверждения: BALANCED читает Wix-страницу, которая повторяет 24 уже покрытых слова D09. Обе её выдержки открыты и совпадают с целевыми; это действительное буквальное совпадение, происхождение текста из него не выводится. PATH эту страницу не читает, но читает Wiki и покрывает все 29 слов. Две новые пары не признаны ложными. Полные выдержки, смещения, source SHA и решение сохранены в `new-baseline-pairs-review.json`.

Семь дополнительных отказов сохранены без обхода ограничений: robots запрещает две страницы; три видео превышают размер ответа; одна страница пуста; одна не ответила вовремя. Наличие записи об отказе не означает, что её содержимое проверено. Отчёты с такими ограничениями остаются частичными, уникальность не устанавливается.

Файлы `dev-final-same-reply-url-v1/fills/*.json` содержат намерение до GET, полный результат либо тип ошибки, отдельные timestamps и происхождение URL. Дополнительные URL получены только из сохранённой выдачи и обычного выбора ссылок родительской страницы. Эталонные URL используются только при подсчёте после выполнения.

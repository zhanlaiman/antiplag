# Отзыв одного токена владельца

Реализация разделена на R-reader и R-writer. Reader-коммит — `3ee23de1f998628220a83132bf4d77a9bc44fa37`; writer следует отдельным коммитом. Их публикацию и точные release SHA/image подтверждает основной чат. Эта рабочая ветка не выполняет deploy, push или logout реального пользователя.

Изменения касаются backend авторизации и его проверок. Web-файлы, зелёный дизайн, поиск, отчёты, API-ключи, owner ID, ключ подписи и действующие квоты сохраняются. В тестах используются только временные БД, синтетические credentials и loopback HTTP.

## R-reader: проверка отзыва

После проверки подписи, ID пространства и подписанного срока действия owner-cookie сервер читает список отзыва в `beta.sqlite3`. Соединение открывается через канонический URI с `mode=ro`: отсутствующий файл нельзя незаметно заменить пустой БД.

Таблица `owner_session_revocations` содержит два поля:

| Поле | Создание и хранение | Чтение |
| --- | --- | --- |
| `token_sha256` | SHA-256 полного проверенного значения токена, включая подпись; первичный ключ SQLite | Совпавший digest запрещает этот токен |
| `expires_at` | Подписанный срок действия, преобразованный в целое число | Проверяется наличие колонки; её значение не отменяет отзыв. Действительный срок берётся из подписанного токена |

Сырые токены и cookie не сохраняются в таблице, диагностике или backup manifest. Другой nonce даёт другой полный токен: отзыв A не отзывает B. API-ключи сохраняют отдельную существующую авторизацию.

Отсутствующая таблица совместима со снимком до включения writer. Ошибка открытия или чтения, повреждённая БД и неверная схема дают `503 owner_session_unavailable`, а не доступ владельца. При старте и чтении новая таблица не создаётся. Кеш разрешённых owner-токенов не добавляется.

Reader отдельно оставляет старый cookie-only logout. Само наличие reader ещё не означает, что выход отзывает токен.

## R-writer: сохранение отзыва

Только точный `POST /api/owner/logout` пропускает создание гостевой identity, admission, аренду tenant и расход лимита модифицирующих запросов. Host/Origin и JSON/body-limit проверяются по-прежнему. Исключение из общего persist устанавливается внутри logout route после этих проверок и сбрасывается для каждого нового запроса. Другие маршруты не меняются.

Для действительного подписанного неистёкшего токена выполняется следующая последовательность:

1. Открыть уже существующую БД через `mode=rw`.
2. В `BEGIN IMMEDIATE` создать таблицу при необходимости и выполнить `INSERT OR IGNORE` с явными колонками `token_sha256, expires_at`.
3. В той же транзакции проверить наличие строки нужного digest. Посторонний UNIQUE-конфликт не должен молча подтверждать выход.
4. Завершить SQLite commit, затем persist.
5. Только после успешного persist подтвердить выход и очистить owner-cookie.

Повторный явный logout одного токена оставляет одну строку и снова вызывает persist. Так можно завершить предыдущую попытку с неизвестным исходом. Автоматический повтор не добавляется. Для отсутствующего, поддельного или истёкшего токена очищается только cookie; таблица отзыва, tenant и квоты не создаются и не изменяются.

При исчезновении `beta.sqlite3` после старта операция не создаёт пустую auth-БД. Ошибка SQL, commit или persist возвращает `503 owner_logout_unavailable` без очистки cookie. Уже зафиксированная локальная строка отзыва никогда не удаляется в качестве компенсации.

Неизвестный исход persist не доказывает удалённую сохранность записи после потери локального состояния или восстановления старого снимка. Оператор сверяет текущий Volume и завершает запись явным повтором. До этого успех не подтверждается. Уже авторизованные задания не объявляются отменёнными.

## Порядок выпуска и откат

1. Отдельно квалифицировать и опубликовать reader; закрепить точный release source/image как baseline отката.
2. Затем отдельно квалифицировать и опубликовать writer.
3. После включения writer откатывать код только на reader-aware baseline, сохраняя текущий Volume, таблицу отзыва и ledger. Старые v33/v34 не читают отзыв и не подходят для отката. Восстановление backup до отзыва может вернуть доступ отозванным токенам и не является допустимым обычным откатом.

Reader-fallback сохраняет отказ для уже отозванных токенов. Новые logout на нём снова имеют cookie-only семантику до возврата writer: это ограничение аварийного baseline, а не равноценная замена writer.

Первоначальная замена на 39 source POST упёрлась в существующий лимит 37 источников; failed log сохранён, лимит и runtime ради fixture не менялись.

Дополнительный fault RED воспроизвёл `200/new empty DB` до введения `mode=rw`. Финальный regression требует `503/no-cookie-clear/no-new-file`. Изменён только способ открытия БД в logout, без изменения общего connect или startup.

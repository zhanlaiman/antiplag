# Отзыв одного токена владельца

На этапе R-reader включено только чтение отзыва. Logout сохраняет прежнее поведение до отдельного R-writer; наличие reader не означает, что выход уже отзывает токен. Ниже описаны оба этапа и обязательный порядок их публикации.

Изменение затрагивает только backend авторизации и локальные проверки. Фронт, дизайн, отчёты, поисковые алгоритмы и настройки провайдеров не меняются. Реальные сессии пользователя не выходят из системы ради проверки.

## Контракт reader

Криптографическая проверка cookie по-прежнему проверяет подпись, ID пространства и подписанный срок действия. Затем для каждого действительного owner-токена читается список отзыва в `beta.sqlite3`. Соединение открывается только для чтения: отсутствие файла БД не должно незаметно создавать пустую БД и разрешать доступ.

В `owner_session_revocations` предусмотрены ровно два поля:

| Поле | Создание и хранение | Чтение и действие |
| --- | --- | --- |
| `token_sha256` | SHA-256 полного проверенного значения токена, включая подпись; первичный ключ SQLite | Поиск на каждом запросе с действительным owner-токеном; найденная строка запрещает этот токен |
| `expires_at` | Подписанный срок действия, преобразованный в целое число | Поле схемы читается, но его изменение не возвращает доступ: действительный срок берётся из подписанного токена |

Сырые токены и cookie не сохраняются в таблице, диагностике или backup manifest. Другой nonce имеет другой полный токен; отзыв A не отзывает B. API-ключи проверяются существующим отдельным механизмом.

Отсутствующая таблица совместима со старым снимком до включения writer. Ошибка открытия/чтения, повреждённая БД или неверная схема приводят к `503 owner_session_unavailable`, а не к признанию owner-токена действующим. Новая таблица не создаётся при старте или чтении. Кеш разрешённых owner-токенов не добавляется.

## Контракт writer

Только `POST /api/owner/logout` получает исключение из создания гостевой identity, admission, аренды tenant и расходования лимита модифицирующих запросов. Проверки Host/Origin, метода и JSON/body-limit сохраняются. Исключение из общего persist ставится внутри точного logout route после этих проверок; другие маршруты не меняются.

Для действительного подписанного неистёкшего токена выполняется короткая транзакция `BEGIN IMMEDIATE`: создание таблицы при необходимости и `INSERT OR IGNORE` полного digest/expiry. После SQLite commit выполняется persist. Только после его успешного возврата сервер подтверждает выход и очищает owner-cookie. Никакие строки owner account, отчётов, API-ключей, ключей подписи, квот или поискового ledger не изменяются этим действием.

Повторный явный logout одного токена оставляет одну строку и снова вызывает persist, чтобы можно было завершить неопределённую предыдущую попытку. Автоматический повтор не добавляется. Для отсутствующего, поддельного или истёкшего токена очищается только cookie; таблица отзыва, tenant и квоты не создаются/не изменяются.

Ошибка SQL/commit/persist возвращает `503 owner_logout_unavailable` без очищения cookie. Уже зафиксированная локальная строка отзыва никогда не удаляется в качестве компенсации. При неопределённом исходе persist нельзя утверждать, что недоставленная запись переживёт потерю локального состояния или восстановление старого удалённого снимка: оператор сверяет текущий Volume и завершает запись явным повтором. Успех до этого не подтверждается. Уже авторизованные задания не объявляются отменёнными.

## Порядок выпуска и откат

1. Отдельно квалифицировать и опубликовать R-reader, проверить его чтение и сохранить точный source/image как baseline отката.
2. Затем отдельно квалифицировать и опубликовать R-writer.
3. После включения writer откатывать код разрешено только на reader-aware baseline с сохранением текущего Volume, таблицы отзыва и ledger. Старые v33/v34 не читают отзыв и не подходят для отката. Восстановление backup до отзыва может вернуть доступ отозванным токенам и не является допустимым обычным откатом.

Публикацию и квалификацию точных SHA выполняет основной чат. Эта ветка не выполняет production POST, logout реального браузера, deploy или push.

## Проверка и границы доказательств

Исходный локальный HTTP RED на `12583a51` воспроизводит: copied A остаётся owner после logout/restart; другой токен B действителен; logout получает 429 при daily40 и capacity100. Все данные синтетические, внешний сетевой доступ блокируется.

Тесты используют настоящие SQLite и локальный HTTP, а не подмену маршрутов. Набор reader проверяет совместимость без таблицы, точный полный hash, сохранность другого nonce/API-ключа/данных и отказ при ошибках БД. Набор writer проверяет single-token отзыв, повтор/конкуренцию, лимиты, Host/Origin/JSON, ошибки до и после commit/persist и восстановление SQLite backup с сохранённым отзывом. Подробные команды, RED/GREEN, source identity и результаты будут записаны для каждого отдельного коммита; прохождение ещё не выполненных проверок не утверждается.
